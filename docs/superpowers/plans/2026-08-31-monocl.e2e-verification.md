## Outstanding

None of the following has been performed. Each needs a person at the
keyboard, and none may be inferred from the code.

- **The Deny path.** Revoke MonoCl's access to `Claude Code-credentials`
  in Keychain Access, relaunch, click Deny, and confirm: the usage dots
  stay dim, the menu reads "Keychain access denied" with a Retry item,
  and **no further dialog appears for at least three poll intervals**.
  This is the criterion that matters most, because the failure it guards
  against — re-reading the keychain on a timer and raising a modal dialog
  every cycle — only manifests for a user who declines, which nobody does
  while testing. Note that an ad-hoc signature changes on every rebuild
  and a keychain grant is bound to the signature, so a prompt reappearing
  after a REBUILD is expected and is not this defect (`DEFERRED.md` item 3).
  The dim dots and the menu text are now reachable without Keychain
  Access — see *Reproducing credential states* below — but the absent
  second dialog is not, and that is the half this entry exists for.
- **Sleep and wake.** The dots should blank until the next successful
  fetch rather than showing a value from before the sleep, and a prior
  Deny should survive the wake without re-arming the dialog.
- **Immediate threshold response.** Dragging the warning threshold below
  the current session percentage should turn that dot amber at once, not
  at the next poll up to sixty seconds later.
- **The critical state.** No usage window has been above 90% during
  testing, so the red state has not been seen rendered.
- **No token in the unified log.** `log show --last 10m --predicate
  'subsystem == "net.sinistral.monocl"' | grep -ciE 'sk-ant|Bearer|accessToken'`
  should report 0. The log was empty during this session, which is
  consistent with the app logging only errors, but an empty log does not
  exercise the redaction.

## Reproducing credential states

A Debug build reads `MONOCL_FAKE_CREDENTIAL`, and when it is set takes
its credential from a fake rather than the keychain. Accepted values are
`valid`, `expired`, `not-found`, `denied`, `malformed` and `unexpected`.
This exists because the authorization dialog interrupts the foreground
and cannot be answered by an unattended run at all.

The variable must reach the process, which rules out the launch form
used above. `open -a` hands the app to launchd, and launchd does not
carry the shell's environment, so the app finds no variable, reads the
keychain, and raises the dialog — looking exactly like the fake having
no effect. Launch the executable directly, or pass `--env`:

```bash
MONOCL_FAKE_CREDENTIAL=denied \
  ~/Library/Developer/Xcode/DerivedData/MonoCl-*/Build/Products/Debug/MonoCl.app/Contents/MacOS/MonoCl
```

A Debug build logs `Using fake credential: <value>` under subsystem
`net.sinistral.monocl`, category `credentials`, when the variable did
arrive.

What it reaches: how MonoCl *responds* to each credential state. Launch
with `MONOCL_FAKE_CREDENTIAL=denied` and the usage dots stay dim, the
menu reads "Keychain access denied", and the Retry item appears.

What it does not reach, and why the Outstanding items above still stand:

- **The dialog itself.** The fake never reaches the keychain, so it can
  raise no dialog and can therefore demonstrate nothing about a second
  one. "No further dialog for three poll intervals" needs a real grant,
  really revoked, and a person to click Deny.
- **Displayed percentages.** Only the credential boundary is faked; the
  HTTP boundary is real, and the real endpoint rejects a fake token. So
  the threshold and critical-state items still need a live login.

## Cosmetic finding, visible only in rendering

The platform line reads as a run-on: `Platform Partially Degraded Service`.
Labels pad to nine characters, and "Platform" is eight, so it receives a
single space where "Session" receives two and reads as a column. Legible,
but that line looks like prose rather than a label and a value. Not
recorded as a defect; noted because it is the kind of thing no test sees.
