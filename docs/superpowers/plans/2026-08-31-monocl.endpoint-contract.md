# Usage endpoint contract

Established 2026-08-31 by hand against the live endpoint (plan Task 0).
This document is the authority for the request shape and response
decoding; where the design spec or the implementation plan disagrees with
it, this document wins.

## Request

```
GET https://api.anthropic.com/api/oauth/usage
Authorization: Bearer <accessToken from the login keychain>
Content-Type: application/json
```

```
with    http_code=200
without http_code=200
```

The beta identifier `anthropic-beta: oauth-2025-04-20` is **optional**:
the endpoint returned 200 both with and without it. MonoCl does not send
it — a header the endpoint does not require is an assumption with no
upside, and one fewer thing to be wrong when the endpoint changes.

## Response

Eighteen top-level keys were observed. Alongside `five_hour` and
`seven_day` there are per-model weekly windows, a weekly window for
OAuth apps, spend and extra-usage objects, a dashboard-availability
flag, and several keys that appear to be internal feature or experiment
names. None of those are enumerated here: they are not part of any
contract, they are Anthropic's internal business, and a list of them in
this repository would only rot.

**Only `five_hour` and `seven_day` are consumed. Every other key is
ignored, and the key set must be expected to change without notice.**

Each consumed window, as observed:

```json
{
  "utilization": 18.0,
  "resets_at": "2026-08-31T17:50:00.568709+00:00",
  "limit_dollars": null,
  "used_dollars": null,
  "remaining_dollars": null,
  "locked_reason": null
}
```

### Two corrections to what the design originally assumed

The spec's first draft inferred both of these from static inspection of
Claude Code's bundle, specifically its status-line mapping
(`used_percentage: five_hour.utilization * 100`). That mapping operates
on Claude Code's **already-normalised internal state**, not on this
response, so reading it as a description of the endpoint was wrong.

| | Originally assumed | Actually observed |
|---|---|---|
| `utilization` | fraction, 0–1, needing `* 100` | already a percentage, 0–100 (`18.0`, `14.0`) |
| `resets_at` | epoch seconds (a number) | ISO-8601 timestamp **string** |

Consequences for the implementation:

- `percent` is `utilization` taken unchanged. A stray `* 100` would
  report 1800%, which would pin both usage lights to critical
  permanently — a failure that looks like a real quota emergency.
- `resets_at` is parsed as ISO-8601. The observed form carries six
  fractional-second digits and a `+00:00` offset; the fractional part is
  not guaranteed, so a `Z`-suffixed form without it is accepted too.
  Anything unparseable throws rather than yielding a wrong date, because
  a silently-wrong reset time feeds the staleness rule and would blank or
  un-blank a light for the wrong reason.

## Credential

`claudeAiOauth.expiresAt` was observed as a **13-digit** value, i.e.
epoch milliseconds.

```
expiresAt digits: 13
```

The unit is undocumented, so the decoder accepts epoch seconds as well
rather than resting on a single observation. The discriminator is
unambiguous: 10^11 seconds is the year 5138, so any value above that
threshold is milliseconds.

## What was not established

- Whether the response shape is stable. It is undocumented and
  unversioned; plan Task 15's opt-in drift check exists for exactly this
  and now also asserts the two properties corrected above.
- Whether `utilization` is ever reported above 100. Nothing observed
  suggests it, and the threshold evaluation does not assume a ceiling it
  cannot enforce.
- No token was displayed, logged, or written to disk at any point during
  this probe.
